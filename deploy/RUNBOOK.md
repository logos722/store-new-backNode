# Gelion: установка и эксплуатация

## Что подготовлено и что ещё требуется

Код рассчитан на один чистый Ubuntu 24.04 x86_64 VPS. Образы собираются на GitHub, а не на сервере. Требуются минимум 2 vCPU, 4 ГБ RAM, 60 ГБ SSD, публичный IPv4, доступ к GHCR/Docker Hub, исходящий SMTP. Рекомендуется 8 ГБ RAM и 80+ ГБ диска. Проверить отсутствие конфликта подсети `172.30.55.0/24`.

VPS ещё не приобретён, DNS и GitHub Secrets не настроены. Никаких реальных сертификатов, паролей, данных каталога или резервных копий в репозитории нет. Старые пользователи и заказы из XML не восстанавливаются.

## 1. Перед установкой

1. Создать VPS в РФ без панели управления. Включить MFA кабинета, автоплатёж, уведомления о балансе, резервный контакт и сохранить доступ к консоли провайдера. Аналогично включить автопродление домена.
2. Проверить `curl -I https://ghcr.io/v2/` (401 допустим), доступ к Docker Hub и SMTP-хосту на нужном порту. Не отключать проверку TLS для обхода сетевых проблем.
3. Посчитать размер изображений. Для временного согласованного снимка нужен свободный диск примерно вдвое больше объёма XML, изображений и дампа БД, плюс запас для ОС и двух версий образов. Проверить `df -h` и `du -sh` перед импортом.
4. Создать независимого администратора с ключом SSH и sudo. Проверить второе подключение и доступность консоли провайдера. Обычный SSH в этих скриптах использует порт 22.
5. Скопировать проверенную папку `deploy` на VPS. Запустить `sudo bash deploy/bin/bootstrap.sh`. Скрипт предназначен для чистого сервера: устанавливает Docker из официального apt-репозитория и Nginx из Ubuntu, открывает 22/80/443, убирает стандартный сайт Nginx. Конфигурация приложения остаётся в `/opt/gelion`, владелец root.

## 2. Секреты и MongoDB

От root выполнить в `/opt/gelion`:

```bash
umask 077
cp /path/to/deploy/mongo.env.example mongo.env
cp /path/to/backend/.env.example backend.env
cp /path/to/deploy/images.env.example images.env
cp /path/to/deploy/backup.env.example backup.env
openssl rand -hex 32  # отдельное значение для КАЖДОГО пароля/JWT
```

Заполнить файлы редактором, не передавая секреты в командной строке или историю shell. Пароли MongoDB генерировать в hex, чтобы они не требовали URL-кодирования в `MONGO_URI`. Пароль `MONGO_APP_PASSWORD` должен совпадать с паролем в URI пользователя `gelion`; authSource — `gelion`. Root Mongo используется только инициализацией/резервированием, приложение получает readWrite только своей БД.

Инициализационный JS выполняется только на пустом `/opt/gelion/data/mongo`. Изменение env-файла не меняет уже созданные пароли; для ротации выполнить `db.updateUser` и затем изменить env. Не удалять каталог БД ради смены пароля.

Настроить SMTP и `PUBLIC_URL`/`IMAGE_HOST=https://gelionaqua.ru`. Проверить SPF, DKIM, DMARC у действующего почтового провайдера; записи MX сохраняются при изменении A-записей сайта. Для 587 установить `SMTP_SECURE=false` (STARTTLS), для 465 — true. Если хостер блокирует SMTP, согласовать разблокировку или поддерживаемый почтовым провайдером альтернативный порт до запуска.

Для приватных GHCR-пакетов выполнить от root `docker login ghcr.io` с отдельным токеном `read:packages`, вводя пароль через stdin. Пользователь деплоя этот токен не получает. Приложения и Mongo запускаются с лимитами памяти и ротацией логов. Mongo не имеет опубликованного порта.

## 3. Первый образ и первый запуск

1. Опубликовать изменения в ветках, проверить pull request CI, затем объединить в `master`. До готовности сервера deploy-job может завершаться ошибкой, но publish-job выдаст digest. Образы: `ghcr.io/logos722/store-new` и `ghcr.io/logos722/store-new-backnode`.
2. Скопировать **оба** digest из build-job в `images.env`: полное имя `ghcr.io/...@sha256:<64 hex>`. Теги `latest` не используются. `images.env` и вся инфраструктура доступны на запись только root.
3. Выполнить:

```bash
cd /opt/gelion
docker compose --env-file images.env config --quiet
docker compose --env-file images.env pull
docker compose --env-file images.env up -d --wait --wait-timeout 180
curl -f http://127.0.0.1:3000/health
curl -f http://127.0.0.1:5000/health/ready
systemctl enable gelion.service
```

Фронтенд собран с публичным доменом; внутренний URL API передаётся при запуске. `.next` создаёт только Next.js, контейнер запускает standalone `server.js`. Локальный `next start` предназначен для разработки/проверок.

## 4. HTTPS и DNS

Поставить A-записи `gelionaqua.ru` и `www` на IPv4 VPS, TTL 300. Удалить устаревшие AAAA, если IPv6 не настроен. Сохранить почтовые TXT/MX. Проверить разрешение обоих имён с внешней сети. HTTP-конфигурация уже обслуживает ACME challenge.

```bash
sudo bash deploy/bin/enable-tls.sh admin@example.com /absolute/path/to/deploy
```

Для получения публичного сертификата HTTP-01 домены уже должны разрешаться на VPS. Если DNS до приёмки менять нельзя, сначала проверить через hosts/`curl --resolve` с временным локальным сертификатом либо получить сертификат DNS-01 у своего DNS-провайдера; временные TLS-ключи не хранить в Git. Не запускать штатный deploy до действующего публичного HTTPS: он проверяет внешние маршруты.

Nginx проксирует API напрямую в Express, `/images/` в статические файлы Express, остальные страницы в Next.js. `/api/web-vitals` остаётся у Next.js. Входящие Forwarded-заголовки заменяются, общий доступ к API во время резервирования/импорта временно получает 503. Антиспам-лимиты работают и в Nginx, и в Express.

## 5. SSH-деплой и GitHub

Сгенерировать новый отдельный ключ Ed25519; старый ключ считать раскрытым из-за прежнего debug-шага workflow. Удалить его из authorized_keys и обоих GitHub Secrets, проверить и удалить журналы с фрагментами ключа. Приватный ключ не хранить в репозиториях.

В root-owned `/etc/ssh/authorized_keys/gelion-deploy` добавить одну строку:

```text
restrict,command="/opt/gelion/bin/ssh-entry.sh" ssh-ed25519 PUBLIC_KEY
```

Права 0644, владелец root; домашний authorized_keys для этого пользователя не используется. Аккаунт не входит в группу docker. Sudo разрешает только root-owned `deploy.sh`, который принимает лишь frontend/backend и SHA256 digest из фиксированного GHCR namespace. Скрипт нельзя заменять файлом пользователя деплоя.

В **обоих** GitHub-репозиториях создать Environment `production` без ручного approval для автоматического выпуска и указать Secrets:

| Secret | Значение |
| --- | --- |
| SSH_HOST | IPv4 или DNS VPS без схемы |
| SSH_USER | gelion-deploy |
| SSH_PRIVATE_KEY | Новый приватный ключ CI |
| SSH_KNOWN_HOSTS | Проверенная строка host key сервера |

Получить fingerprint сервера через консоль провайдера (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) и сверить с отдельно полученным known_hosts. Не использовать слепой `ssh-keyscan` внутри workflow.

После независимой проверки входа администратора выполнить `sudo bash deploy/bin/harden-ssh.sh --verified-admin-key-login`: пароли и root-вход отключатся. Защитить `master` обязательными CI-проверками. Изменения после merge автоматически собираются и выкатываются; workflow_dispatch также выпускает только master.

Оба workflow сериализуются серверным flock. Обновляется только нужный сервис, без `compose down`. При неуспехе readiness или внешнего HTTP-check возвращается прежний digest, workflow завершается ошибкой. Деплой не меняет схему/данные БД.

Ручной откат от root:

```bash
previous=$(cat /opt/gelion/state/backend.previous)
sudo /opt/gelion/bin/deploy.sh backend "${previous##*@}"
```

Не удалять предыдущие GHCR-образы. После проверки работающего выпуска можно удалять только явно устаревшие локальные образы, без volumes; автоматической очистки Docker volumes здесь нет.

## 6. Внешние копии и уведомления

Создать приватный S3 bucket у другого провайдера/в независимом аккаунте. Выдать отдельному ключу доступ только к bucket/prefix копий. Restic шифрует данные до отправки. Записать случайный пароль в `/opt/gelion/secrets/restic-password` (0600) и сохранить его и доступ к S3 **вне VPS**, иначе восстановление после потери сервера невозможно.

Заполнить root-owned `backup.env` с shell-кавычками (не Compose-синтаксис). Инициализировать **один раз**:

```bash
sudo -i
cd /opt/gelion
set -a; source backup.env; set +a
restic init
/opt/gelion/bin/backup.sh
restic snapshots
```

Скрипт закрывает запись и останавливает backend на время mongodump и архивации картинок/XML, затем возобновляет работу до отправки в S3. Большой архив увеличивает паузу: измерить её на реальном каталоге. Диск MongoDB напрямую не копируется. Plaintext-дампы удаляются после выполнения; при аварийном выключении проверить `/var/lib/gelion-backup*` и файл maintenance перед возвращением трафика. Копии удерживаются 14 ежедневных + 8 еженедельных, дедупликация restic включена. `restic check` выполняется после копирования, полный `restic check --read-data` — ежемесячно вручную.

Секреты не входят в автоматический backup: отдельно сохранить защищённую копию SMTP/JWT/Mongo env, инфраструктуры и GHCR-доступа в менеджере секретов. Ротация credentials инициализации Mongo потребует отдельной проверки восстановления.

Скопировать `msmtprc.example` в `/etc/msmtprc`, заполнить SMTP, права 0600; записать адрес получателя в `/opt/gelion/alert-email`. Протестировать `sudo /opt/gelion/bin/notify.sh test`. Затем:

```bash
systemctl enable --now gelion-backup.timer gelion-check.timer
systemctl list-timers 'gelion-*'
```

Копия выполняется около 03:00 по Москве; проверка каждые 5 минут проверяет HTTPS, готовность БД, свободный диск, сертификат и свежесть копии. Ошибки systemd отправляются через msmtp. Проверить получение письма, не только exit code.

В backend-репозитории отдельно включить внешнюю проверку: repository variable `MONITOR_ENABLED=true`, Secrets `MONITOR_SMTP_HOST`, `MONITOR_SMTP_PORT`, `MONITOR_SMTP_USER`, `MONITOR_SMTP_PASS`, `MONITOR_EMAIL_FROM`, `MONITOR_EMAIL_TO`. Эти секреты — repository-level: monitor не использует production environment. Запуск каждые 15 минут из GitHub, письмо при переходе в ошибку. GitHub schedules могут задерживаться или отключаться при неактивности репозитория; для строгого SLA подключить независимый uptime-сервис с теми же HTTPS endpoints.

## 7. Каталог и импорт

Скопировать `import.xml` и `offers.xml` в `/opt/gelion/data/xml`, изображения — в `/opt/gelion/data/images/import_files/...`, сохраняя пути из XML. Выдать чтение UID 1000 контейнера, без права записи: каталоги 0755, файлы 0644. XML и изображения не попадают в Docker build context.

```bash
sudo /opt/gelion/bin/import.sh --replace-catalog
```

Сначала создаётся успешная внешняя копия, затем проверяются XML, дубликаты ID, числовые поля, схема и существование изображений. Полная новая коллекция и индексы создаются отдельно, затем переключаются атомарным rename. Ошибка подготовки не удаляет текущий каталог. Заказы и пользователи не заменяются. Импорт не запускается при рестарте контейнера.

## 8. Восстановление и приёмка

Проверить восстановление конкретного snapshot в изоляции:

```bash
sudo /opt/gelion/bin/restore-drill.sh SNAPSHOT_ID
```

Создаётся новый `/opt/gelion-restore.*`, Mongo работает без сети и опубликованных портов; после проверки контейнер удаляется, восстановленные данные остаются для сравнения. Сверить количество товаров/заказов/пользователей, выборочные цены и картинки. Цель 4 часа — проверяется измерением полного восстановления, а не обещанием скрипта.

При полной потере VPS: создать новый сервер, повторить bootstrap, восстановить доступ к S3/пароль restic и секреты, выполнить restore drill, перенести восстановленные изображения/XML и дамп в новый Compose, загрузить дамп через mongorestore с root auth, выставить сохранённые digest, запустить приложения, проверить и только затем направить DNS. Не запускать импорт XML поверх восстановленной БД. Перенос восстановленного Mongo data-dir между версиями не использовать; работать через logical dump.

Перед запуском проверить:

- Каталог, фильтры, поиск, карточки, изображения, SSR и sitemap, неизвестную категорию/товар (404).
- Регистрацию/вход и JWT, заказ с правильной суммой, сохранение заказа и получение письма с XLSX; сбой SMTP не должен терять сохранённый заказ.
- Независимые и одновременные push в оба репозитория, успешный деплой и намеренно неисправный образ с откатом. Автоматический rollback проверять только на контролируемом тестовом выпуске.
- Перезапуск контейнеров и VPS без потери БД/изображений и без запуска XML-импорта.
- Из внешней сети закрыты 3000, 5000, 27017; доступны только SSH/HTTP/HTTPS. Проверить `certbot renew --dry-run`.
- Действительную внешнюю копию, восстановление из неё, email-уведомления и настройки автоплатежей.

Первые сутки после DNS-переключения проверять ошибки и реальные заказы. Рабочие команды: `docker compose --env-file images.env ps`, `journalctl -u gelion-backup`, `journalctl -u gelion-check`, логи Nginx. Не публиковать логи с данными клиентов и секретами.
